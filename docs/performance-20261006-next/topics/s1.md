# S1: phase-specific concurrency budgets

Independent baseline f8638be9. Worktree /Users/callen/.codex/worktrees/mold-s1-phase-concurrency/mold; branch codex/mold-s1-phase-concurrency.

Prototype control: `MOLD_PHASE_BUDGET=merge:N`, `copy:N`, or `gc:N`. Only one chosen phase enters a separate N-worker Rayon pool; all other work retains the normal adaptive linker pool (32 workers for the large corpus cases). Pool creation remains inside whole-link measurement and has a phase_pool_init timer. Budget >= the current worker count simply preserves the existing path, including all one-worker links. Root should initially screen N=8 and 16 on copy, merge, and GC, then expand only justified cases. This is an experimental control, not a proposed stable command-line API.

Safety: phase entry points hold no WorkerLocal guards. Local scratch created inside a capped phase sizes itself to that pool. Existing persistent WorkerLocal storage clamps indices and serializes slot access with mutexes; the targeted phases do not retain a local-slot lock while crossing pools. Nested Rayon operations run inside the selected pool rather than accidentally returning to the global pool. Independent background jobs may still use the global pool, so this caps the selected phase rather than claiming a global process CPU limit. No host affinity/governor settings change.

There is an intrinsic cost: additional pool startup and idle global workers. A neutral result should include that cost, not subtract it from headline latency. The wrapper leaves section/symbol order, ownership, relocations, diagnostics, and output bytes unchanged. Actual worker-count attribution and golden outputs under every screened budget are required.

Independent static review (merge_ownership): no concrete deadlock or borrow issue. Selected-pool nested entry returns directly because its worker count is already at the cap; installation joins before borrowed phase state escapes. OnceLock initialization does not re-enter the wrapper. Global background GDB jobs may run concurrently, so this is a foreground-phase budget rather than a process-wide limit. Merge coverage includes resolve and resolve_sections, excluding member gathering, section creation, and later allocated layout. Copy coverage includes copy_chunks for normal, relocatable, and separate-debug output, but compressed-debug preparation performs earlier copying outside this wrapper. Copy cap8 lowers lld CPU and latency, and substantially lowers Clang CPU with a small latency increase. Rust-analyzer latency regresses substantially. A threshold chosen between these corpus sizes would risk fitting the benchmark set, so no adaptive threshold is proposed. The wider eight-case confirmation below retained the same tradeoff. Merge caps generally increase latency; GC caps are neutral or exchange lower CPU for longer latency. Neither is recommended as a blanket default.
