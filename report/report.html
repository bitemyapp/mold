mold: moving polling and startup into Rayon

6 October 2026 · Builds, tests and measurements on ssh wx-workstation.

Both experiments retain roughly the original PRs’ performance; neither establishes a broad additional efficiency win. Across eight equally weighted workloads, the polling prototype reduces median elapsed time by 0.63% while using 1.43% more CPU than #1694. The startup prototype takes 0.86% longer with essentially unchanged CPU (0.08% more) than #1695. These are descriptive geometric means; most per-case intervals include zero.

The polling branch’s clearest single-link gain is lld: 78.61 → 76.20 ms (3.1% less time; paired interval 0.1–4.5%). Its drawbacks are Rust hello CPU (+6.0%) and concurrent stripped-Clang linking: 1.532 → 1.566 s per 48-link batch (+2.2% elapsed and +6.1% CPU). That throughput regression remains after narrowing polling to top-level idle workers.

The startup branch preserves the fixed startup saving: C hello is 6.84 ms, versus 6.92 ms for #1695 and 7.75 ms for the shared baseline. Most original-versus-Rayon differences are small; full Clang is 1.8% slower in this sample, while the concurrent Clang batch is effectively tied. Hello throughput is too noisy to establish a difference between the two startup implementations.

Recommendation: the async-startup branch is the cleaner candidate for a Rayon API discussion. The idle-timeout branch demonstrates that mold’s timer hooks and polling jobs can be removed, but its concurrent-load CPU cost needs more work before treating it as an efficiency improvement. Both APIs still require upstream Rayon review.

These branches patch vendored rayon-core 1.13.0. The APIs are experimental and are not available in released Rayon. Each branch descends from its original PR; both comparisons share baseline 99d79c42.

Implementation and correctness

Polling: ThreadPoolBuilder::idle_timeout(Duration) extends idle search between completed top-level jobs, leaving initial startup and nested join/scope waits on the normal policy. Zero retains the original policy. Mold removes its broadcast polling jobs and timer hooks, and opts into 2 ms.

Startup: ThreadPoolBuilder::build_global_async() moves the spawn helper into Rayon and preserves the global pool, thread names, stack sizes and callbacks. A single current worker needs no helper. Synchronous helper-creation errors are returned; later worker-creation failures abort rather than leave a worker queue permanently unserviced. This error policy requires upstream API review.

Baseline and both candidates pass the mold native suite: 503 passed, 14 skipped, zero failures each. Upstream Rayon tests and added lifecycle/startup/failure tests pass. Captured link outputs are byte-identical across all arms and tested worker counts. No claims are made about untested target architectures.

Measurement limits

AMD Threadripper PRO 9985WX; CPUs 32–63, one hardware thread per core; warm inputs; ext4 output; --no-fork; same compiler and release flags. Each build cleans the affected packages to prevent cross-checkout Cargo cache reuse. The original PRs and their exact parent are tested, without later upstream changes. Three warmups precede 40 single-link samples, with 50 ms between processes.

Unrelated workstation build/VM activity occurred. Interleaving reduces time-order bias but does not remove shared-memory, storage or scheduler interference. Bootstrap intervals describe this sample and do not account for every systematic effect. The p95 figures are descriptive with 40 samples; extreme-tail estimates are not reliable. Equal-weight geometric means, where quoted, describe these eight cases and are not a production-workload forecast.

Internal --perf pass profiles are retained separately from uninstrumented timings. Their millisecond resolution and overlapping nested/concurrent spans limit fine attribution; do not sum nested spans or treat those CPU counters as per-section CPU attribution.
